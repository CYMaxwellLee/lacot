## 一、P0｜還原機條件化重訓（字典 v1）

### 1.1 唯一的變因

encoder / VQ-EMA / dead-code restart / 超參數 / 切段法 / split_seed **全部照 M0**
（`experiments/m0_gait_dict/m0_common.py` 逐項對照），**只改 decoder 的輸入**：

```
M0 無條件版： decoder(字 embedding 16)                       -> 4 步動作段 (32)
P0 字典 v1  ： decoder(字 embedding 16 ‖ 正規化段起點 obs 29) -> 4 步動作段 (32)
```

obs = `concat(qpos(15), qvel(14))`，29 維（已用真資料驗證與資料集 `observations`
逐位元相等）。正規化統計＝**訓練切分**段起點 obs 的 mean/std，存進 ckpt buffer
（P1/P2 一律讀 ckpt 裡那份，⛔ 不重算）。

## 二、P1｜重放測試（四組對照）

### 2.1 設定

- 取樣來源＝**官方 held-out val 檔**（`antmaze-medium-stitch-v0-val.npz`，500 集），
  ⛔ 不是段級切分的 val（那些段跟訓練段同集）。固定 seed=20260908 抽 **1000 個視窗**，
  每視窗模擬 H=80 步 ⇒ **每個字典組 20,000 段**（要求 ≥10,000）。
- 目標＝真螞蟻在第 gs 步時的 xy；限時 N 有兩把尺一起印：
  - `N_data` ＝ gs（**真螞蟻自己走完這一段用掉的步數**，最緊、自我校準）
  - `N_table` ＝ 量尺包 distance→steps 的 p50（同距離、全資料）← P2 要用的那把
- 到達＝任一步 `|pos - goal| <= 0.5`（ogbench 的 ant goal_tol）。
- 五組：`true`（真動作直放）／`true_chunkcmp`（真動作但每 chunk 重置、位移累加）／
  `dict_indep`（字典段獨立重放）／`dict_cont`（字典連續重放）／
  **`dict_randcode`（打假球對照：同一台還原機、同一個重置協定，但字是亂挑的）**。
  ⭐ 兩個對照組都是特意加的：`true_chunkcmp` 讓 `dict_indep` 分得清「字典準」還是
  「每 4 步重置讓誤差沒機會累積」；`dict_randcode` 回答更凶的一題 ——
  **這個量測到底分不分得出好字跟壞字**。⛔ 沒有它，下面那張表不能用。

### 2.2 🚨 判定尺自檢：先定位，再開藥

第一次跑（goal 放在 +40 步）`true` 這組只有 **54%**，離「應接近 100%」很遠。
照工單這裡要停手回報「判定尺有問題」。**先定位了，結論不是尺壞掉：**

- **float64 round-trip 誤差恆為 0**（自己產生 float64 狀態 → set_state 回去 → 重放
  80 步，逐位元相同）⇒ 模擬器完全決定性，⛔ 不是 RNG、不是 solver 狀態、
  不是 warmstart（清零組與 base 一模一樣）。

  螞蟻的接觸動力學把它放大：8 步內還在 goal_tol 內，12 步開始破，40 步已經崩掉。
- ⇒ **「真動作開環重放」的可重現視窗大約 8～12 步。** 這是資料＋物理的性質，
  ⛔ 不是判定尺的錯、⛔ 也不是字典的錯 —— 但它**封頂了任何開環重放對照能講的話**。

**開的藥（不是繞過，是把量測放回可量的區間）**：一次模擬、四個 goal horizon
（gs = 8/12/20/40）全部一起印，`true` 當每一格的天花板。gs=8/12 是尺有效的區間；
gs=20/40 保留，因為**天花板自己也在掉**，那正是要給主人看的東西。

1. 在尺有效的區間（gs≤12），`dict_cont` 92.2 vs 天花板 98.3（N_data 1.25N）——
   連續執行的字典比真動作只掉 6 個點。
2. gs=40 時 `dict_cont` 47.4 vs `true` 55.7：差 8.3 點，⛔ 但兩者都被 float32 混沌
   壓在 50% 附近，這一格**量到的主要是混沌、不是字典**。
3. `dict_indep` 對它自己的對照組 `true_chunkcmp`：末端誤差 0.199 vs 0.121。

### 3.2 機制與紀律

每個 chunk：枚舉 32 個字 → 各用還原機（吃當下 obs）展開 4 步 →
`env.unwrapped.step` 前瞻執行 → 選終點離 `planner.sub` 最近的字 → 還原狀態 → 實走。

擋掉的四個雷（都在 `lacot_vqo.py` 的 docstring 逐條記著）：
1. 前瞻走 `env.unwrapped.step` ⇒ ⛔ 不動 `TimeLimit._elapsed_steps`
   （用 wrapped `env.step` 的話 32×4 的前瞻會讓每一集提早 128 倍被截斷）。

### 3.5 判讀：字典沒有在走路，它在原地磨蹭

```
它【沒有】的毛病：不翻倒（逐步 0.00%）、不抽搐（比真螞蟻還平滑）、
                  不塌成單一字（32 字全活、perplexity 28.64/32）、
                  還原機也沒壞（前瞻與實走逐位元相同）
它【有】的毛病：走太慢 —— 每步位移只有真螞蟻的 37%，
                而且走不到 —— per-leg .063、全鏈 .100，兩項都輸給前任 lo 頭
```

⭐ 步速疊圖（`results/p2_vqo_speed_overlay.png`）**一眼就看得出來**：真螞蟻那條在
0.13 附近有個漂亮的峰，vq_oracle 那條整團塌在接近 0 的地方 —— 這正是 plan 第二關
（分佈關）設計來抓的東西。⚠️ ⛔ 但它抓到的**不是「爬行」**：軀幹 z 中位數正常、
翻倒率 0.00%。是「站著原地磨」，不是「趴著爬」。

⇒ **P2 判準（預釘 ≥ .448）：不過，而且不是差一點，是差 4.5 倍。**
照 plan 的分岔條款：**⛔ 不進 M2 選字頭（P4），回頭修字典。**

**為什麼會這樣（機制上的解釋，⚠️ 是推論不是量測）**：
oracle 的選法是 plan 指定的「終點離路標最近」，這是**貪心、一個 chunk 的視野**。
一個 chunk 只走 ~0.5 公尺，而路標在 7.5 公尺外 ⇒ 每次都挑「這 4 步能往路標多推一點點」
的字。這種選法沒有辦法維持步態的**相位連續性**（螞蟻要連續好幾個 chunk 走同一種
步法才跑得起來），結果就是每 4 步換一種步法、互相打斷 ⇒ 步速掉到 37%。
⭐ 這跟 P1 的結果完全一致：P1 裡字典**照著真步法字串**走時步速是 0.1356（貼合真螞蟻），
一換成貪心選字就掉到 0.0490 —— **壞的不是字典，是選字的方式。**

🚨 **所以這個上界要標清楚它界的是什麼**：
它是「**32 字 × 貪心單 chunk 前瞻**」的上界，⛔ **不是「這本字典的表達力」的上界**。
真正的表達力上界要用多 chunk 前瞻／字串 beam search 去逼（P1 已經證明存在一條
字串能把真螞蟻的步態走出來）。⇒ 「回頭修字典」之前，⭐ 建議先確認到底是
**字典不夠好**還是**選字視野太短**（這兩者的藥完全不同）。

## 四、判讀（一句話）

**會走，但走不到。** 字典能把真螞蟻的步態壓進 32 個字再展開回來 —— 展開的動作
不翻倒（逐步 0.00%）、不抽搐（比真螞蟻平滑）、照著真字串走時步速貼合真螞蟻
（0.1356 vs 0.1325）、每段位移誤差只有 0.06 公尺。但一接上接力實戰、改用
「每 chunk 貪心挑最靠近路標的字」，步速掉到真螞蟻的 37%、per-leg 到達率 .063、
全鏈 .100 —— **輸給它要取代的 lo 頭（.288/.124），更遠不及主頭（.448/.320）。**

依據：P1 §2.4（字與狀態的邊際貢獻，字換掉重建 MSE 從 .105 → .423）證明字典有內容；
P1 §2.5（步速 0.1356 貼合、翻倒 1.1%、平滑度不抽搐）證明展開出來的是像樣的步態；
P2 §3.4（步速 0.0490、per-leg .063）證明貪心選字把它毀了；
P2 §3.2 的前瞻忠實度自檢（誤差恆為 0）排除「oracle 挑錯字」這個解釋。

   float32 的 qpos/qvel（float64 round-trip 誤差恆為 0 ⇒ 排除 RNG／solver／warmstart），

   ⛔ 別拿它們當「字典差」的證據。
2. **限時到達率在「每 chunk 重置＋位移累加」協定下是鈍尺**（§2.3 對照組）。
   已改用末端誤差與每段位移誤差當主判準，⛔ 但這代表 plan 裡「第一關」的原始設計
   在 P1 這個場景**沒有鑑別力**（P2 的接力場景是連續的、不受此限）。
