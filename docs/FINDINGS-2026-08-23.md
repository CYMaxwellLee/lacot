## 0. 🚨 最重要的結果 — 補上 cond 之後，`u` 沒有貢獻

_⚠️ 本節在 2026-08-23 深夜被自己的後續實驗改寫過一次。先讀這段，再讀 0-b 的舊版。_

`[實測]` K=4 ＋ head 吃 `[cond, u]`，**三個 seed**，官方 eval（MAXH 1000、100 集）：

| | seed0 | seed1 | seed2 |
|---|---|---|---|
| LaCoT R=3 closed | 0.860 | 0.740 | 0.940 |
| LaCoT R=3 open | 0.850 | 0.760 | 0.920 |
| **null-u floor**（`head(cond, 0)`） | **0.850** | **0.770** | **0.930** |
| LaCoT R=0（不 refine） | 0.640 | 0.620 | 0.510 |
| ORACLE closed | 0.600 | 0.700 | 0.710 |
| GCBC floor（⚠️ 容量不公平，見下） | 0.590 | 0.620 | 0.630 |

🚨 **`null-u floor` 跟 LaCoT R=3 幾乎一模一樣** ⇒ **把 `u` 整個歸零，成績不掉。**
head 學會了只看 `cond`、忽略 `u`。⇒ 這一版的 LaCoT 已經退化成一個 GCBC。

🚨 而 **`LaCoT R=0` 比 null 還差**（0.51~0.64 vs 0.77~0.93）
⇒ **未經 refine 的 `u` 對 head 是噪聲**；refine 的作用是「把噪聲消掉」，不是「加價值」。

### 這是一個設計上的兩難，不是調參問題

- head **沒有** `cond` ⇒ `u` 被迫扛位置資訊 ⇒ 看起來有用（0.700），但餵 OOD 的 u 就崩（ORACLE 0.120）
- head **有** `cond` ⇒ `u` 變成可有可無 ⇒ 方法退化成 GCBC

⇒ **要讓 LaCoT 成立，`u` 必須攜帶 `cond` 沒有的東西。** 候選方向（⏳ 待主人裁示）：
① 讓 `u` 只負責長程意圖，`cond` 只給即時位置；
② 對 `cond` 做 dropout，逼 head 學會用 `u`；
③ 重新設計 `e_target` 的訓練目標，讓它與 `cond` 的資訊不重疊。

### ⚠️ 兩個必須連帶修正的

**(a) GCBC baseline 容量不公平**：腳本裡的 `gcbc_head` 只有 1 個 hidden layer，
而 LaCoT 的 head 有 3 層。⇒ 真正該當 baseline 的是 **`null-u floor`（0.85）**，不是 0.59。

**(b) 真正的天花板已經量到了**（`scratch_calib.py`，同一套 rollout harness）：
```
BFS 專家（尊重牆）    100/100 = 1.000   <- 真正的天花板
直線控制器（忽略牆）    25/100 = 0.250   <- eval 不是靠直線就能過
```
⇒ 這個 eval **可解、且不簡單**。以後對標 **1.000**，⛔ 不要再用那個 OOD 的 ORACLE。

## 0-b.〔已被 0 改寫〕舊版：LaCoT 贏 GCBC，open-loop 贏 closed-loop

⚠️ **以下是 head 【未吃 cond】的單 seed 版本。**補上 cond 後 `u` 的貢獻就消失了（見第 0 節）——
這一欄仍有價值：它顯示「當 head 被迫只能靠 `u`」時，refine 過的 `u` 確實能撐起 0.700。

`[實測]` K=4、官方 eval 標準（MAXH 1000、100 集）、head 未吃 cond：

| 變體 | success |
|---|---|
| **LaCoT R=3 open**（想一次、照著走） | **0.700** ★ |
| LaCoT R=3 closed（每 chunk 重想） | 0.630 |
| GCBC floor（無 u） | 0.410 |
| ORACLE closed（每 chunk 重問 BFS） | 0.120 |
| LaCoT R=0（flow 直接採樣，不 refine） | 0.000 |
| null-u floor（`head(0)`） | 0.000 |

**① LaCoT 贏 GCBC 29 個百分點** —— 第一次在最終指標上贏，不是 BC loss。
**② open-loop 贏 closed-loop**（0.700 > 0.630）—— 「想一次然後照著走」贏過「每 4 步重想」。
這正是 LaCoT 的核心主張，而且是量出來的：**想出來的那條路禁得起放著不管**。
**③ refine 是主力不是配角**：R=0 是 0.000、R=3 是 0.63~0.70。

⇒ ⛔ **08-22 的「refine 只是弱的一步改善器、沒有 test-time scaling」在 success rate 上不成立。**
那個結論是用「對齊 e_target 的 cosine」量的 —— 而 refine 做的事根本不是對齊 e_target，
是**把 u 搬到 head 能用的地方**。用錯指標就會得到相反的結論。

### 🚨 而「ORACLE = 天花板」這個框架是錯的

ORACLE 只有 0.120，**低於 LaCoT 的 0.700**。⇒ 它不是上界。

`[推論]`（未驗）原因是 **OOD**：ORACLE 餵的 e_target 來自 `expert_positions()` **模擬**的
BFS 路徑，而 head 訓練時只看過兩種 u —— 資料集軌跡的 e_target、以及 refine 後的 u。
oracle 餵的是**第三種、從沒看過的**分布。

⇒ **ORACLE 是一個 OOD 壓力測試，不是天花板。** 08-22 與本文件先前版本都把它當天花板解讀，
包括「u 還欠 0.51」那種說法 —— **那個數字沒有意義**。

⇒ 若要一個真正的上界，應該餵 head **訓練分布內**的最佳 u（例如資料集裡的真實 hindsight
軌跡），而不是另一個規劃器產生的路徑。

⚠️ **限制**：單一訓練 seed、pilot 規模（6000 步 vs 官方 1,000,000）、K=4 且 head 未吃 cond。
要多 seed 才算數。

## 1. 維度是主因 — flow 一直沒問題

`[實測]` 掃 `K`（PerceiverPooler 的 latent 數，`dim = K × 256`），每格從頭訓一次，
同 cond、同步數，並帶 e_target 健康度與退化控制：

| K | dim | e_target match-acc | flow mode | flow T=1 | regression | 打亂 cond |
|---|---|---|---|---|---|---|
| 64 | 16384 | 0.899 | 0.523 | 0.465 | 0.947 | ~0 |
| 32 | 8192 | 0.937 | 0.540 | 0.466 | 0.943 | ~0 |
| 16 | 4096 | 0.910 | 0.647 | 0.560 | 0.951 | ~0 |
| 8 | 2048 | 0.911 | 0.891 | 0.804 | 0.954 | ~0 |
| **4** | **1024** | **0.911** | **0.934** | **0.877** | **0.954** | ~0 |

**flow 的對齊 0.523 → 0.934，跟 regression 的差距從 0.424 縮到 0.020。**
`match-acc` 全程 0.899–0.937 沒有下滑 ⇒ e_target 沒有被犧牲，這是淨進步。
打亂 cond 全程 ~0 ⇒ 不是灌水。

**為什麼**：`u` 是 `K×D_MODEL` 維，而它描述的軌跡只有 `T_CAP × 2 = 32` 維真實內容。
K=64 時是 **512 倍的膨脹**。regression 對此無感（只是參數多），flow 要在整個空間建密度，
被維度直接壓死。

⇒ `[實測]` **「flow 的 mode 放錯位置」這個結論是錯的** —— mode 一直放得對，是 16384 維的
空間讓它採不到。本文件先前版本的那個判斷已作廢。

⇒ 這也讓「flow vs regression」的對立消失：K=4 時兩者準度相當，而 flow 還多帶著 exact
likelihood（能評估想法好壞）、多候選採樣（test-time scaling 的入口）、可微密度
（value-directed refine 要用的地形）。

### 沿路排除掉的兩個假設

`[實測]` **尺度不匹配 → 排除**：`||true_et||` = 129.7 ± 2.6，flow base 期望 `√16384` = 128.0，
比值 1.013。

`[實測]` **高維採樣散開 → 有，但只佔一小段**：溫度 1.0 → 0.0 只把對齊從 0.468 拉到 0.523
就 plateau。真正的差距不在採樣。

`[實測]` **p(e|cond) 很窄**：(s,g) 幾乎相同的 135 組，e_target 互相的 cosine 0.840
（隨機配對基準 0.022）。在 navigate 上路徑接近唯一。
⚠️ `[推論]` 早先由此推出「stitch 有多模態所以 flow 有用」——**未經驗證**，而且查過
OGBench 之後不確定成立：navigate 與 stitch 是**同一個 env、同一組 task goal**，只差在
資料收集方式（`gymnasium` 註冊表裡沒有 `-navigate-`/`-stitch-` 的 env）。stitch 的困難
`[推論]` 是「訓練時看不到長距離 (s,g)、要靠組合」，這跟多模態是不同的東西。**待驗**。

## 2. Oracle 證明的比宣稱的少

`[實測]` 讀 `scratch_m4_oracle.py` 得到三件事：

**① 它是 closed-loop。** `rollout` 每個 chunk（4 步）都用當下的 obs 重新呼叫
`env.unwrapped.get_oracle_subgoal()` —— 環境內建的 BFS。所以不是「想一條路照著走」，
是每 4 步問一次導航。head 只需要翻譯剛算好的路徑前幾個點。

**② e_target 的來源與訓練時不同。** 訓練用資料集的真實 observations；oracle 用
`expert_positions()` 自己模擬的簡化點動力學（`xy += 0.2*a`，沒有 MuJoCo 慣性）。
餵 OOD 的東西也能 100% ⇒ e_target 空間很寬容。

**③ 訓練與 eval 的 goal 距離差一個量級。** 訓練 `geometric(p=0.02)` 平均 ~50 步；
eval 實測 start-dist 27.9、每步最多 0.2 ⇒ 需要 140+ 步。而 `T_CAP=16` 個取樣點要
覆蓋的長度差了近 3 倍。

**④ 〔本節初版寫錯，已更正〕** 初版寫「`scratch_m4_oracle.py` 用 `ActionMLP` 取代
`DiscretizedActionHead`，所以那天的數字是**替身**的」——**這個判斷是錯的**。
`[主人]` 那不是疏失，是 08-22 當天發現離散 head 不行之後**刻意改成 MLP** 的。

`[實測]` 而今天的 head 診斷等於把那個決定重新證明了一次（同一個真 e_target、同樣 5000 步，
共同指標＝decode 回連續 action 的 MSE）：

| head | MSE @5k |
|---|---|
| MLP + MSE（08-22 改用的） | **0.375** |
| Discretized 32 bins ＋同樣 3 層 MLP | 0.845 |
| Discretized 256 bins ＋同樣 3 層 MLP | 0.903 |
| Discretized 256 bins（本體原樣，單層 proj） | 1.286 |
| 猜資料集平均（什麼都不學） | 0.494 |

⇒ 補到同容量之後，離散 head 仍然**比什麼都不學還差**。cross-entropy 對「落在隔壁 bin」
不給任何分數，而那正是連續控制需要的訊號。bin 數有影響但很小（32 每格都優於 256，
`[主人]` 昨天講的方向成立），不是主因。

⇒ **行動**：把 MLP head 正式寫進本體（`lacot/heads.py::ContinuousActionHead`），
`LaCoTActorState` 預設改用它，`DiscretizedActionHead` 加上「連續控制別用」的警告。
本體與實際做法脫節，正是這次誤判的成因。

⇒ 正確讀法：那個 100% 是「**closed-loop BFS ＋ MLP head 的翻譯能力上限**」，
不是 LaCoT 這個方法的上限。「架構證明完美」的說法作廢 —— 但理由是 ①②③（closed-loop、
e_target 來源、goal 距離），**不是** head 的問題。

### 修正：closed-loop vs open-loop

- **closed-loop**：每個 chunk 重算 u。錯誤不累積。跟官方比較要用這個（官方 GCBC 甚至每步重決策）。
- **open-loop**：u 只在起點算一次，全程沿用；cond（自己在哪）仍每 chunk 更新。
  凍住的是「想出來的那條路」。

⇒ `[推論]` **兩者的差距本身就是 reasoning quality 的直接量測**：差距小 = 想出來的路
禁得起放著不管。LaCoT 若要主張「會推理」，證據在 open-loop 那一欄。

## 5. 🚨 維度的權衡（⚠️ 前提後來被推翻了一半，先讀這段）

⚠️ **下面這組數字是在【action head 只吃 `u`、沒吃 `cond`】的前提下量的。**
⚠️⚠️ 而且ルナ一度把 ORACLE 的 0.120 歸因於「head 沒吃 cond ⇒ 閉著眼睛開車」——
**那個解釋不成立**：同一版 head 也沒吃 cond，LaCoT 卻拿到 0.700。閉著眼睛開不出 0.700。
真正的嫌疑是 OOD（見第 0 節）。cond 該補仍然該補（多給資訊不會壞），但它不是 0.120 的成因。
`[實測]` 後來發現本體的 head 只餵 `u`（08-22 的腳本是餵 `[cond, u]`），而這個差異讓
K=4 的 ORACLE 從 100% 掉到 **12/100**。⇒ K 小的劣勢有一大部分其實是「位置資訊被壓掉、
而 head 沒有 cond 可問」造成的，不是維度本身。**cond 補回之後要重跑，⛔ 別直接沿用下表。**

（已修：head 輸入改 `cond_dim + k*d_model`；驗證方式＝同一個 `u` 餵不同 `cond`，
動作差異 0.5599 ⇒ cond 確實進到動作裡。）


`[實測]` 同一支 head 診斷在 K=64 上再跑一次（其他不變）：

```
                  K=4 (1024維)   K=64 (16384維)
flow 對齊            0.934          0.523      ← 降維救了 flow
action head MSE      0.375          0.278      ← 降維【傷了】head（差 35%）
```

`u` 的維度同時是兩件事 —— flow 要建模的空間**大小**（要小才學得動）與 action head 能讀到的
資訊**容量**（要大才預測得準）。**兩個需求方向相反**，而我們一直用同一個數字同時壓它們。

⇒ 這回頭解釋了 08-22：K=64 時 oracle 能到 100%（head 資訊夠）但 LaCoT 本身很低
（flow 生不出好 u）。那個落差不是「flow 不行」，是**同一個維度綁死了兩個對立的需求**。

`[推論]` 候選解法：**解耦**。flow 在低維生 `z`，再用 decoder 展開成高維 `u` 餵 head：
```
cond ──flow──► z（低維，好採樣） ──decoder──► u（高維，資訊足） ──► action
```
「想」在低維、「執行」在高維 —— 也更貼近 CoT 的原意：念頭本來就是壓縮的，展開是後面的事。
⏳ 等主人判斷方向。

## 6.5 🚨 cond 的效果（三個 seed）＋ 一個很強的對比

`[實測]` head 補上 `cond` 之後，K=4 三個 seed：

| | ORACLE closed | ORACLE open |
|---|---|---|
| 無 cond（單 seed） | 0.120 | 0.010 |
| 有 cond seed 0 | **0.600** | 0.000 |
| 有 cond seed 1 | **0.700** | 0.000 |
| 有 cond seed 2 | **0.710** | 0.000 |

⇒ **cond 讓 ORACLE closed 從 0.12 跳到 0.60~0.71（+0.5）。**

⚠️ **ルナ在這裡過度否定了自己一個正確的診斷。** 先是判斷「head 沒吃 cond 是 0.120 的主因」
（對的），接著因為「同一版 head 也沒吃 cond，LaCoT 卻有 0.700」就整個推翻它，改口說主因是
OOD。**那個反駁是錯的** —— 兩個因素是**相乘**的：
- head 沒有 `cond` ⇒ 位置資訊只能從 `u` 讀
- ORACLE 的 `u` 又剛好是 OOD ⇒ 讀不出來 ⇒ 崩到 0.120
- 而 LaCoT 的 `u` 是 in-distribution ⇒ 讀得出來 ⇒ 就算沒有 cond 也有 0.700

⇒ 補上 `cond` 等於給 head 一個**獨立於 `u`** 的位置來源，OOD 的傷害就被吸收掉了。
⛔ 教訓：**一個反例只能否定「唯一主因」，不能否定「是主因之一」。**

### 🚨 而 ORACLE open 三個 seed 全是 0.000 —— 對比極強

```
BFS 算出的「客觀正確路徑」，放著不管走完全程   ->  0.000
LaCoT 自己想出來的 u，放著不管走完全程        ->  0.700（無 cond 版實測）
```

`[推論]` ORACLE 的 `e_target` 編的是**從起點出發的絕對座標軌跡** —— agent 一走，那條路
就過期了。而 LaCoT 的 `u` 經過 refine，看起來編的是**更適合持續執行的東西**（可能偏向
相對方向或策略，而非絕對路徑）。

⇒ 如果 LaCoT 的 open-loop 優勢在多 seed 下站得住，**這會是「LaCoT 的 u 不是路徑、
而是更好用的東西」的直接證據** —— 那正是 latent CoT 該有的樣子。⏳ 等三個 seed 的 LaCoT 欄。

## 7. ⚠️ 一個解讀上的變化：`null-u floor` 不再是「地板」

`[實測]` head 改吃 `[cond, u]` 之後，`head(cond, 0)` 就等於「從 (s,g) 直接預測 action」
—— 也就是一個 GCBC。訓練 3000 步的實測：

```
無 cond：null 0.4597  gcbc 0.2408   <- null 接近「猜平均」(0.494)，是真地板
有 cond：null 0.2336  gcbc 0.2356   <- 幾乎一模一樣 => null 就是 GCBC
```

⇒ ⛔ 不要再把 `null-u floor` 讀成「什麼都不學的地板」。它現在是 **BC baseline**。
⇒ 這其實更有用：**`anchor` 或 `refine` 減掉 `null`，直接就是「u 帶來多少 GCBC 以外的價值」**。
⇒ 也代表舊版那個 `null-u floor = 0.000` 的 rollout 數字**不能跟新版並排**。

（順帶 `[實測]`：三個 seed 在 3000 步的 anchor 是 0.199 / 0.218 / 0.290 —— seed 之間
差距不小，證實了單一 seed 不足以下結論。）
